# Bounded GPOS mark input filtering

With `layout`, the ordinary MarkToBase, MarkToLigature and MarkToMark helpers
now apply the selected lookup's GDEF filtering to the current input glyph,
including ExtensionPos lookups. They share SinglePos/PairPos filtering:
IgnoreMarks takes precedence over UseMarkFilteringSet, which takes precedence
over MarkAttachmentType. An excluded lookup does not prevent a later eligible
lookup from supplying an anchor. Zero-valued anchors remain successful matches.

This is a bounded, runtime-verified HarfBuzz15-compatible input-filter change,
not a claim of complete OpenType conformance. Microsoft chapter2's general
lookup-flag discussion distinguishes current glyph from other input glyphs;
HarfBuzz's top-level application additionally checks current-glyph properties.
The original fixtures establish the exact behavior implemented here.

Do not apply the same filter to the attachment target. IgnoreBaseGlyphs and
IgnoreLigatures do not invalidate otherwise usable base/ligature anchors.
Predecessor search, lookup order, component ownership, and coordinate conversion
are unchanged. In particular, lookup-specific MarkToMark predecessor skipping
and ligature ownership remain separate work.

Missing GDEF, missing GlyphClassDef, and unclassified glyphs retain the existing
`includes_glyph` policy: no Unicode class is invented and the input is admitted.
For a glyph actually classified as a mark, missing/out-of-range filter sets or
missing/nonmatching attachment classes reject that lookup. This compatibility
policy is not HarfBuzz's Unicode-derived class fallback.
The malformed/missing mark-filter-set policy is also intentionally different:
HarfBuzz15 admits the original fixture with a missing set table or out-of-range
set index and applies its anchor, while this implementation rejects that lookup
for a GDEF-classified mark, matching the existing SinglePos/PairPos helper.
These missing-data cases are safety/compatibility controls, not HB parity tests.

## Remaining GDEF fallback

The renderer still treats MarkAttachClassDef or AttachList evidence as permission
for its historical synthetic base-origin placement when no GPOS anchor applies.
This patch does not redesign that fallback. Thus a rejected GPOS anchor can
still result in a mark at the base origin rather than the cursor. The fixture's
`attach_mismatch` face and the helper-level unit test deliberately establish
both facts: no usable GPOS anchor, but unchanged base-origin fallback. Do not
claim final-position HarfBuzz parity for this case.

No no-GPOS heuristics, generic mark advance zeroing, script/language selection,
Japanese residual-mark geometry, or font substitution provenance were changed.
Hiragino's observed residual-mark overlap is not repaired by this patch.

## Bounded real-font control

An independent read-in-place run compared unchanged main and this patch on
Arial5.01.2x, Georgia5.00x-4, NotoSansCJKjp2.004 and installed Hiragino Sans W3.
Six cases, five locale settings and four orientations (480 runs) were
byte-identical in serialized positions, advances, bounds and outline hashes.
These are regression controls, not universal shaping/browser parity.

Arial `!` + U+0301 makes the retained fallback visible: at UPEM2048, fontcore
places acute at x0 in both versions, whereas HarfBuzz15 places it at x569 (the
cursor). Arial `q` + U+0301 remains correctly anchored at (825,328) in Y-down
coordinates in both versions and HarfBuzz. The mixed above/below stack remains
outside this patch's predecessor/order claims. System fonts were not copied or
modified. Japanese residual marks and authored Noto vertical behavior remained
unchanged in the controls.
